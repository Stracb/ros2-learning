# 一、环境与软件源

## 坑 1：照着老教程装 ROS 2，命令失效

**现象**：`sudo apt-key add -` 报错，或加了源之后 `apt update` 失败。

**原因**：ROS 2 官方在 **2025 年改了安装方式**。老办法（`apt-key` + `ros2.list`）
已经废弃。

**解决**：用新的 `ros2-apt-source` 配置包：

```bash
sudo apt install curl
export ROS_APT_SOURCE_VERSION=$(curl -s https://api.github.com/repos/ros-infrastructure/ros-apt-source/releases/latest | grep -F "tag_name" | awk -F'"' '{print $4}')
curl -L -o /tmp/ros2-apt-source.deb "https://github.com/ros-infrastructure/ros-apt-source/releases/download/${ROS_APT_SOURCE_VERSION}/ros2-apt-source_${ROS_APT_SOURCE_VERSION}.$(. /etc/os-release && echo ${UBUNTU_CODENAME:-${VERSION_CODENAME}})_all.deb"
sudo dpkg -i /tmp/ros2-apt-source.deb
```

**教训**：**网上教程的时效性要自己判断**。看到 `apt-key add` 就知道是旧教程。

---

## 坑 2：`apt update` 慢到 12.8 kB/s

**现象**：`apt update` 某个源要跑好几分钟，平均速度只有 12 kB/s。

**原因**：**不是镜像慢**，而是 `security.ubuntu.com`（美国服务器）反复超时重试，
把平均速度拖垮了。

**解决**：把安全源也换成国内镜像：

```bash
sudo sed -i 's|http://security.ubuntu.com/ubuntu|http://mirrors.tuna.tsinghua.edu.cn/ubuntu|g' /etc/apt/sources.list.d/ubuntu.sources
```

**结果**：速度从 12.8 kB/s 变成 **4,643 kB/s**（快了 360 倍）。

**教训**：**看到"慢"，先分清是"下载慢"还是"等待慢"。**
用 `apt update` 的输出看有没有 `Ign:`（忽略）和重试。

---

## 坑 3：`grep -r` 找不到 `ros2.sources`

**现象**：`grep -rl "packages.ros.org" /etc/apt/sources.list.d/` 返回空，
但文件明明存在。

**原因**：`ros2.sources` 是一个**符号链接**（指向 `/usr/share/ros-apt-source/ros2.sources`）。
**`grep -r` 默认不跟随符号链接。**

**解决**：
- 用 `grep -R`（大写 R，会跟随符号链接）
- 或直接用 `cat` 看内容
- 或 `ls -l` 确认它是不是链接

**教训**：**`-r` 和 `-R` 不一样**。R = 跟随符号链接。

---

## 坑 4：镜像选错，下载慢

**现象**：一开始用清华 TUNA 下 ROS 2 包，速度 5 MB/s；换个镜像后变 11 MB/s。

**原因**：不同镜像对不同资源的同步和带宽不一样。

**解决**：**实测比选**。用 curl 测同一文件在不同镜像的速度：

```bash
curl -s -o /dev/null --max-time 10 -w "%{speed_download}\n" <某个文件的 URL>
```

**第 1 天实测结果**（ROS 2 源）：

| 镜像 | 速度 |
|---|---|
| 中科大 USTC | **4.3 MB/s**（最快，选它）|
| 南大 NJU | 2.4 MB/s |
| 清华 TUNA | 2.0 MB/s |
| 阿里云 | 198 KB/s |
| 北外 / 上交 | 重定向，不可用 |

**教训**：**别迷信"最大牌"的镜像，实测最快才是最快。**

---

## 坑 5：Ubuntu 24.04 默认不启用 `noble-updates`

**现象**：装 ROS 2 时报依赖找不到。

**原因**：Ubuntu 24.04 全新安装时，apt 源可能只含 `noble` 基础套件。

**解决**：检查并补齐：

```bash
grep -A2 "^Suites:" /etc/apt/sources.list.d/ubuntu.sources
# 应该包含 noble noble-updates noble-backports
```

**教训**：装大件之前先确认源是完整的。

# 二、虚拟机与 VMware

## 坑 6：虚拟机建在 `E:\VMware\` 里，报"拒绝访问"

**现象**：新建虚拟机时提示无法打开配置文件，拒绝访问。

**原因**：`E:\VMware\` 是 **VMware 的程序安装目录**。
里面的子文件夹权限受限（`Everyone` 只有 `ReadAndExecute`，**没有写权限**）。

**解决**：虚拟机建到别的地方，比如 `E:\Ubuntu-24.04.5\`。

**教训**：**虚拟机不要放在程序安装目录里。** 三个理由：
1. 权限受限
2. 重装/卸载 VMware 可能被一起删掉
3. 备份和排错混乱

---

## 坑 7：快照占掉几十 GB（**已解决，留作教材**）

**现象**：虚拟机文件夹一路涨到几十 GB。

**原因**：拍快照时勾选了「**拍摄虚拟机内存**」。
本机内存 12 GB，**每个快照就把 12 GB 内存存一份**。

**解决**：拍快照时**取消勾选**「拍摄虚拟机内存」。

| | 勾选内存 | 不勾选 |
|---|---|---|
| 每个快照 | **12 GB** | **几百 MB** |
| 恢复后 | 直接回到当时桌面 | 重新开机（20 秒）|

### 第 9 天复核的实测（**唯一口径**）

直接读虚拟机的 `.vmsd` 快照清单 + 文件大小，实测：

| 快照（显示名）| 状态文件 | 内存文件 |
|---|---|---|
| `07-画正方形以及参数化` | `Snapshot6.vmsn` 6.4 MB | **`Snapshot6.vmem` 12.13 GB** |
| `10-参数与launch巩固` | `Snapshot8.vmsn` 6.4 MB | **`Snapshot8.vmem` 12.13 GB** |

```
E:\Ubuntu-24.04.5\  总计 38.88 GB
├── Snapshot6.vmem  ← 内存快照，白占         12.12 GB
├── Snapshot8.vmem  ← 内存快照，白占         12.12 GB
└── 真正的虚拟硬盘（3 个 vmdk）             约 14.6 GB
```

→ **两个快照各自拍了内存，合计白占约 24.2 GB**（12,416 MB × 2，实测值）。

> **历史说明（已被推翻的旧结论）**：本文件一度写"两个快照都**没有拍内存**，这件事已经处理完了" ——
> 那是**只在快照管理器里看了一眼名字**，根本没去看文件。
> **"看过界面"不等于"验证过事实"**，与坑 57 是同一类毛病。

**教训**：
- **快照要选"不拍内存"**，代价只是恢复时多等 20 秒
- 拍完**顺手看一眼文件夹大小**（`Get-ChildItem E:\Ubuntu-24.04.5 | Measure-Object Length -Sum`）

## 坑 8：删除快照 ≠ 回滚

**现象**：以为"删掉快照 = 回到那个状态"，结果删完还在被搞坏的状态里。

**原因**：混淆了两个操作。

| 操作 | 效果 |
|---|---|
| **转到快照** | 回到那个状态（丢弃当前改动）|
| **删除快照** | 只是把存档删掉，**当前系统状态原样不变** |

**解决**：要回滚就用「转到」，要清理存档才用「删除」。

**教训**：**搞清楚"回滚"和"清理"是两件事。**

## 坑 9：GUI 程序在 SSH 终端跑不了

**现象**：在 VS Code 终端跑 `ros2 launch` 或 `ros2 run turtlesim turtlesim_node`，
报错：

```
qt.qpa.xcb: could not connect to display
[ERROR] [turtlesim_node-1]: process has died
```

**原因**：VS Code Remote-SSH 建立的终端**没有图形显示环境**（没有 `DISPLAY`）。

**解决**：**GUI 程序必须在虚拟机自己的桌面终端运行。**

| 程序类型 | 在哪里跑 |
|---|---|
| **要弹窗口**（turtlesim / RViz / Gazebo）| **虚拟机桌面终端** |
| **纯计算**（发布者、订阅者、服务端…）| 哪里都行 |

**教训**：判断标准很简单 —— **要不要弹窗口。**

# 三、Gazebo 与图形

## 坑 10：Gazebo 界面持续频闪

**现象**：`gz sim shapes.sdf` 能启动、不报错，但 3D 视图**一直闪**。

**原因**：Gazebo Harmonic 默认用 **Ogre2** 渲染引擎。
**Ogre2 与 VMware 的 SVGA3D 虚拟显卡不兼容**。

注意：**这和"3D 加速有没有开"无关** —— 本机 `glxinfo` 显示 `SVGA3D` 正常，
照样会闪。

**解决**：

临时（验证用）：
```bash
gz sim --render-engine ogre shapes.sdf
```

永久（改配置文件，必须改**两个**）：
```bash
# 找到默认配置
GUI_SRC=$(find /usr /opt -name "gui.config" 2>/dev/null | head -1)
SRV_SRC=$(find /usr /opt -name "server.config" 2>/dev/null | head -1)

mkdir -p ~/.gz/sim/8
[ -n "$GUI_SRC" ] && cp "$GUI_SRC" ~/.gz/sim/8/gui.config && \
  sed -i 's|<engine>ogre2</engine>|<engine>ogre</engine>|g' ~/.gz/sim/8/gui.config
[ -n "$SRV_SRC" ] && cp "$SRV_SRC" ~/.gz/sim/8/server.config && \
  sed -i 's|<engine>ogre2</engine>|<engine>ogre</engine>|g' ~/.gz/sim/8/server.config
```

**为什么两个都要改**：
- `gui.config` 管**窗口显示**
- `server.config` 管**服务端渲染**（相机/深度相机等传感器仿真走这条路径）

**教训**：**虚拟机里遇到 Gazebo/RViz 渲染异常，第一反应是"换渲染引擎"，不是怀疑 3D 加速。**

## 坑 11：`glxinfo` 命令找不到

**现象**：想验证 3D 加速，但 `glxinfo` 不存在。

**原因**：没装 `mesa-utils`。

**解决**：
```bash
sudo apt install -y mesa-utils
glxinfo -B | grep "OpenGL renderer"
```

**判断**：显示 `SVGA3D` = 硬件加速正常；显示 `llvmpipe` = 软件渲染（有问题）。

**教训**：环境验证要趁早做，别等装完 Gazebo 才发现。

## 坑 13：话题名 vs 消息类型搞混

**现象**：看到 `/turtle1/cmd_vel` 和 `geometry_msgs/msg/Twist`，
分不清哪个是"频道的名字"、哪个是"数据的格式"。

**原因**：两者的写法都像"用斜杠分段的路径"。

**解决**：记住对讲机类比：

| 对讲机 | ROS 2 |
|---|---|
| **频道**（1 频道 / 5 频道）| **话题名**（`/turtle1/cmd_vel`）|
| **说的话**（中文 / 英文）| **消息类型**（`geometry_msgs/msg/Twist`）|

**两者必须都匹配才能通信。**

**更机械的规则**：
- **带引号的 = 名字**（你自己取，能改）
- **不带引号的 = 类型**（import 来的，不能改）

**教训**：这个混淆持续了 3 天才彻底打通。

---

## 坑 14：以为"包跑起来就变成节点"

**现象**：以为运行一个包 = 产生一个节点。

**原因**：不精确。

**正确理解**：
- **包** = 硬盘上的文件夹（永远是死的）
- **可执行程序** = 包里的某个文件（也是死的）
- **节点** = 程序**被运行后**，在内存里产生的进程（活的）

**一个包可以有很多程序，每个跑起来都是一个独立节点。**

**教训**：**"包"和"节点"是两个层面的东西**（磁盘 vs 内存）。

---

## 坑 15：以为 `grep`/`colcon` 认识 `src` 这个目录名

**现象**：以为 `colcon build` 会去找名叫 `src` 的目录。

**正确理解**：**`colcon` 不认识 "src" 这个词。**
它只是**从当前目录递归扫描，找含 `package.xml` 的目录**。

`src` 只是社区约定的名字，叫别的也行。

**另外**：`build/` `install/` `log/` 里会被 colcon 放一个 `COLCON_IGNORE` 文件，
所以扫描时会跳过它们。

**教训**：**约定 ≠ 规定。** 很多"必须这么写"其实只是"大家都这么写"。

---

## 坑 16：搞不清"话题名"和"服务名"谁定的

**现象**：不知道 `/turtle1/cmd_vel` 和 `movemove` 这两个名字能不能改。

**正确理解**：

| 名字 | 谁定的 | 能改吗 |
|---|---|---|
| `/turtle1/cmd_vel` | **turtlesim 定的** | 改了乌龟就不听 |
| `/turtle1/pose` | **turtlesim 定的** | 同上 |
| **你自己提供的服务名** | **你自己起** | 随便改 |

**一句话**：**用别人的东西 → 服从别人的名字；自己提供的东西 → 自己起名。**

---

## 坑 17：`msg` 里的字段到底是什么

**现象**：不知道 `msg.x` 里的 `x` 从哪来，也不知道 `request`/`response` 有哪些字段。

**正确理解**：

> **类型定义文件（`.msg` / `.srv` / `.action`）里的【每一行】= 一个字段。**
> **字段名就是"类型后面那个词"。**

**查法**：
```bash
ros2 interface show <完整类型名>
```

**`srv` 特殊**：中间有条 `---`
- `---` **上面** → 给 `request`
- `---` **下面** → 给 `response`

**`action` 特殊**：有**两条** `---`，三段
- 第一条上面 → 目标 goal
- 两条之间 → 结果 result
- 第二条下面 → 反馈 feedback

**教训**：**不用背字段名，查一次就知道。**

---

# 五、Python 代码错误

## 坑 18：回调函数没缩进到类里

**现象**：
```
AttributeError: 'Greeter' object has no attribute 'operation'
```

**原因**：`def operation(self, ...)` 写成了**顶格**（0 缩进），
跑到了类外面，所以类里没有这个方法。

**解决**：`def operation` 要**缩进 4 格**，和 `def __init__` **左边对齐**。

**怎么快速检查**：VS Code 里把 `class Xxx` 那一行**折叠**起来 ——
如果方法名跟着消失，说明它在类里；如果还在外面，就是缩进错了。

**教训**：**Python 靠缩进决定"谁属于谁"。同类方法必须左对齐。**
这是本项目**第一个踩的代码坑**（第 4 天，`draw_circle`）。

---

## 坑 19：存的名字和用的名字不一致

**现象**：
```
AttributeError: 'TurtleCircler' object has no attribute 'publisher_'
```

**原因**：
```python
self.publishers = self.create_publisher(...)   # 存进 publishers
self.publisher_.publish(msg)                   # 却用 publisher_
```

**解决**：**统一成一个名字**（建议 `self.publisher_`）。

**教训**：`self.xxx` 像"贴标签" —— **存的时候贴什么，取的时候就得用什么。**

---

## 坑 20：浮点字段赋了整数（会崩溃）

**现象**：
```
python3: ..._vector3_s.c:58: geometry_msgs__msg__vector3__convert_from_py:
        Assertion `PyFloat_Check(field)' failed.
[ros2run]: Aborted
```

**原因**：`msg.linear.x = 2` —— **`2` 是整数（`int`），字段要求浮点数（`float`）。**
ROS 2 的 C 层做严格类型检查，断言失败，程序被强制杀掉。

**解决**：**写小数点。**

| 要写 | 不要写 |
|---|---|
| `2.0` | `2` |
| `1.0` | `1` |
| `0.0` | `0` |

**注意区分**：
- **赋值给消息字段** → 必须浮点（否则崩）
- **做比较运算**（`if msg.x > 10`）→ 整数也行

**教训**：这个坑**踩了两次**（第 4 天 `1` vs `1.0`；第 5 天 `0` vs `0.0`）。
**最阴险的地方是"只在特定条件才崩"** —— 第二次是"乌龟走到边界才崩"。

---

## 坑 21：忘了写 `self.`

**现象**：
```
UnboundLocalError: cannot access local variable 'operation'
                   where it is not associated with a value
```

**原因**：`self.create_service(Trigger, 'say_hello', operation)` —— 少了 `self.`。
Python 把 `operation` 当成一个**局部变量**，但它从没被赋过值。

**解决**：改成 `self.operation`。

**怎么从报错读出来**：报错说它是 `local variable`（局部变量）——
如果写对了，Python 会说这是"方法"，不会说是局部变量。

**教训**：**在类里面引用自己的方法/属性，必须加 `self.`。**
凡是要"交给 ROS 2 以后调用"的函数（回调），前面都要 `self.`。

---

## 坑 22：Python 方法名拼写错误

**现象**：
```
node.destroy.node()      # 点写成了下划线
```

**原因**：`destroy_node` 是 `Node` 类提供的方法名，不能自己造。

**解决**：`node.destroy_node()`

**怎么避免**：用 VS Code 自动补全（打 `node.` 让它弹列表）。

**教训**：**没有工程师背 API 名字，大家都是让 IDE 补全。**

---

## 坑 23：字段名拼写错误

**现象**：
```
AttributeError: 'SetBool_Response' object has no attribute 'messsage'
```

**原因**：`response.messsage`（三个 s），应该是 `message`（两个 s）。

**解决**：改对拼写，或用自动补全。

**教训**：**打 `response.` 让它弹列表**，就不会拼错。

---

## 坑 24：`if __name__ == '__init__'`

**现象**：程序不执行（或者没有明显报错）。

**原因**：写成了 `'__init__'`（构造函数的特殊名字），
应该是 **`'__main__'`**（主程序标志）。

**解决**：
```python
if __name__ == '__main__':
    main()
```

**为什么有时看不出问题**：用 `ros2 run` 启动时，入口脚本会**直接调用 `main()`**，
不经过 `if` 判断，所以**碰巧还能跑**。但直接用 `python3 xxx.py` 就完全不动。

**教训**：`__init__` 和 `__main__` 都是双下划线包起来的，但含义完全不同。

# 六、ROS 2 命令使用

## 坑 25：`ros2 run` 少给参数

**现象**：
```
usage: ros2 run [-h] [--prefix PREFIX] package_name executable_name ...
ros2 run: error: the following arguments are required: executable_name, argv
```

**原因**：只敲了 `ros2 run my_turtle`，没给程序名。

**解决**：`ros2 run my_turtle draw_circle`

**怎么读这个报错**：
- 第一行 `usage:` 是"正确用法模板"
- **方括号 `[]` 里的是可选的，没方括号的是必需的**
- 第二行直接告诉你缺哪个

**教训**：**报错里的 `usage:` 行是金矿** —— 它告诉你正确的写法。

---

## 坑 26：程序名拼写错误

**现象**：
```
No executable found
```

**原因**：`setup.py` 里写的是 `'move_clinet = ...'`（`client` 拼成了 `clinet`），
但运行时敲的是 `move_client`。

**解决**：改对拼写，重编。

**怎么快速定位**：
```bash
ros2 pkg executables my_turtle     # 看实际注册的名字
```

**教训**：**别凭记忆敲命令，先查一下实际有什么名字。**

---

## 坑 27：改了 setup.py 没重编

**现象**：新加的程序跑不了，或者改了代码没生效。

**规则**：

| 改了什么 | 重编？ |
|---|---|
| **已注册文件的内容**（`.py` / launch / config）| ❌ **不用**（`--symlink-install` 生效）|
| **新增文件**并注册到 `setup.py` | ✅ **要** |
| **`setup.py` 本身** | ✅ **要** |
| **不确定** | ✅ **重编，几秒钟的事** |

**教训**：**改【内容】不用重编；改【结构】要重编。**

**为什么"内容"不用重编**：`--symlink-install` 让 `install/` 里的文件是**符号链接**，
指向 `src/` 的源文件。改源码，链接那边立刻就是新的。
**但"新增文件"需要建立新链接 → 必须重编。**

---

## 坑 28：忘了 source 工作空间

**现象**：
```
Package 'my_turtle' not found
```

**原因**：这个终端没有 source 过工作空间，
ROS 2 不知道 `~/ros2_ws/install/my_turtle` 的存在。

**解决**：
```bash
source ~/ros2_ws/install/setup.bash
```

**永久解决**（写进 `~/.bashrc`，新终端自动加载）：
```bash
echo "source /opt/ros/jazzy/setup.bash" >> ~/.bashrc
echo "source ~/ros2_ws/install/setup.bash" >> ~/.bashrc
```

**教训**：**环境变量是每个终端各自一份的。**

---

## 坑 29：`colcon build` 跑错目录

**现象**：编译产物结构混乱，或者找不到包。

**原因**：在 `~/ros2_ws/src` 里跑了 `colcon build`。

**解决**：**必须在工作空间根目录跑**：
```bash
cd ~/ros2_ws
colcon build --packages-select <包名> --symlink-install
```

> **注意**：这里也要带 `--packages-select` —— 工作空间里有接口包时，
> 全量 `colcon build --symlink-install` 会另报一个错（见**坑 47**）。

**教训**：`build/` `install/` `log/` 都会建在"你运行命令的那个目录"下。

# 七、参数与 launch

## 坑 30：YAML 参数文件的文件名打错

**现象**：
```
Couldn't parse params file: ... Error: Error opening YAML file
```

**原因**：文件名拼错了。注意是 **"Failed to parse"** 还是 **"Error opening"** ——
后者说明**文件根本打不开**（路径/文件名错），不是格式问题。

**解决**：用 `ls` 确认实际文件名：
```bash
ls -la ~/ros2_ws/src/my_turtle/config/
```

**教训**：**"打不开"和"格式错"是两类问题**，别混。

---

## 坑 31：以为 `declare` 只是"登记"

**现象**：以为"用哪个参数值"是由 `get_parameter` 决定的。

**正确理解**：**`declare_parameter` 同时决定了用哪个值。**

```
命令行给了 3.0  ──┐
                  ├──▶ declare_parameter('side_length', 1.5)
代码默认 1.5   ──┘         │
                           │ 在这里二选一
                           ▼
                    最终值（命令行优先）
                           │
                           ▼
              get_parameter(...).value  ← 只是"取出"，不做决定
```

**教训**：**`declare` 是"登记 + 决定值"，`get` 只是"取出"。**

---

## 坑 32：`ros2 param set` 改了没反应

**现象**：`ros2 param set /draw_square side_length 5.0` 显示成功，但程序不理会。

**原因**：代码在 `__init__` 里把值存到了 `self.side_length`，
之后一直用那个副本，**不再回头看参数**。

**解决**：想让"运行时改参数"也生效，需要**参数回调**
（`add_on_set_parameters_callback`）—— 更进阶的用法。
**大多数场景只要"启动时传参"就够了。**

**教训**：**"参数值"和"代码里用的副本"是两回事。**

---

## 坑 33：三种参数写法搞混

| 场景 | 格式 | 例子 |
|---|---|---|
| **命令行** | `-p 名:=值`（**冒号等号**）| `-p side_length:=3.0` |
| **launch 文件** | Python 字典 | `parameters=[{'side_length': 3.0}]` |
| **YAML 文件** | YAML | `side_length: 3.0` |

**教训**：**命令行是 `:=`，launch/YAML 是 `: `。**

# 八、服务与动作

## 坑 34：服务回调忘了 `return response`

**现象**：客户端发请求后**一直卡住**，收不到响应。

**原因**：服务端回调忘了最后那行 `return response`。
ROS 2 手上什么都没有，客户端就一直等。

**解决**：回调最后**必须**：
```python
return response
```

**教训**：**服务是"一问一答"，不返回就等于不回答。**

---

## 坑 35：服务名两边不一致

**现象**：客户端一直打印"等待服务..."，卡住不动。

**原因**：客户端的服务名和服务端的服务名不一致。
（实际踩的：客户端写了 3 个 "move"，服务端只有 2 个。）

**怎么查**：
```bash
ros2 service list | grep 关键词
```
看实际注册的服务名是什么。

**教训**：**服务两端只认【服务名 + 服务类型】，必须完全一致。**

---

## 坑 36：以为"客户端不需要服务端也能干活"

**现象**：以为客户端可以独立执行动作。

**正确理解**：
- **客户端只是"下单的人"，真正干活的是服务端**
- **客户端必须有一个服务端存在**，否则 `wait_for_server()` 一直等
- **服务端不会"等不到客户端"** —— 它只待命，没人调用也不卡

**谁找谁**：

| 角色 | 行为 |
|---|---|
| **服务端** | 只"挂牌营业"，等人来（不找任何人）|
| **客户端** | **主动找服务端**，找不到就等 |

**启动顺序不重要** —— 客户端会自己等，服务端随时上线都能接上。

**教训**：**只有客户端会等；服务端永远不卡。**

---

## 坑 37：`geometry_msgs` 和 `turtlesim` 各有一个 `Pose`

**现象**：`import` 写错了类型，运行时在 `msg.x` 那行报错。

**原因**：**有两个同名但内容完全不同的类型**：

```
geometry_msgs/msg/Pose          turtlesim/msg/Pose
├── Point position              ├── float32 x
│   (x, y, z)                   ├── float32 y
└── Quaternion orientation      ├── float32 theta
    (x, y, z, w)                ├── float32 linear_velocity
                                └── float32 angular_velocity
```

**正确写法**（turtlesim 里用乌龟的位置）：
```python
from turtlesim.msg import Pose
```

**教训**：**类型决定了你能访问哪些字段。导错类型，代码看着对，一跑就报错。**
查法：`ros2 topic list -t` 看实际类型。

# 九、Git

## 坑 38：不建 `.gitignore` 会把编译产物传上去

**现象**：`git status` 里出现 `build/` `install/` `log/`，几百 MB。

**原因**：没建 `.gitignore`，或者建晚了。

**解决**：**在 `git init` 之后、`git add` 之前**建好 `.gitignore`：

```gitignore
build/
install/
log/
__pycache__/
*.pyc
.vscode/
```

**检查方法**：`git add .` **之前**先跑 `git status`，
确认输出里**没有** `build/` `install/` `log/`。

**教训**：**提交前一定先 `git status` 看一眼。**

---

## 坑 39：GitHub 不支持密码认证了

**现象**：`git push` 时输密码，失败。

**原因**：GitHub 已不支持账号密码。

**解决**：用 **SSH 密钥**（推荐）或 **Personal Access Token**。

**SSH 配置（一次搞定）**：
```bash
ssh-keygen -t ed25519 -C "邮箱"      # 一路回车
cat ~/.ssh/id_ed25519.pub            # 复制这一行
# 粘到 GitHub → Settings → SSH and GPG keys → New SSH key
ssh -T git@github.com                # 测试
```

**注意**：
- `.pub` 结尾的是**公钥**（给 GitHub 的）
- 没后缀的是**私钥**（**绝不能泄露**）
- 私钥在 `~/.ssh/` 里，**不在 `~/ros2_ws` 里**，所以不会被 git 提交

**教训**：**私钥永远是本地的，公钥才是给别人的。**

# 十、学习方法（元层面的坑）

> 这一类比代码坑更值得记住。

## 坑 40：以为"能读懂"就等于"会写"

**现象**：能看懂代码，但让自己从零写就写不出来，很焦虑。

**原因**：**理解和产出是两种不同的能力。**

| | 读懂 | 写出 |
|---|---|---|
| 大脑在做 | **识别**（"哦，原来是这样"）| **回忆 + 构造**（从零搭出来）|
| 难度 | 低 | 高得多 |
| 怎么变强 | 多看 | **只能靠"真的去写"** |

**类似**：能读懂英文文章 ≠ 能写出英文文章；能看懂菜谱 ≠ 能炒出来。

**解决**：
- **看代码不会让你学会写代码** —— 必须自己动手
- 忘了就查，不丢人

**教训**：**"能读懂但写不出"是必经阶段，不是能力问题。**

---

## 坑 41：试图背下代码

**现象**：想记住每个方法名、每个参数顺序，记不住就焦虑。

**正确认识**：**没有工程师背 API 名字。** 大家都是：
- 用 IDE 自动补全
- 忘了就查文档

**你自己说过**："查表倒是可以知道" —— **这个态度是对的。**

**教训**：**该背的是"结构"，不是"拼写"。**
方法名有规律（`create_xxx` = 建一个，`get_xxx` = 拿一个），记住规律比记住单词有用。

---

## 坑 42：不知道"要背什么"

**现象**：分不清哪些必须记住、哪些可以查。

**分三类**：

| 类型 | 例子 | 怎么处理 |
|---|---|---|
| **必须形成肌肉记忆** | `colcon build` 的流程 | 反复做，不用刻意背 |
| **必须理解** | 发布/订阅模型、状态机 | 反复撞见 → 理解自然加深 |
| **查一下就行** | `package.xml` 有哪些字段、方法名拼写 | **压根不用记** |

**教训**：**大部分焦虑来自"想记住第三类"。**

---

## 坑 43：不记得"哪些写了 1 遍、哪些写了 2 遍"

**现象**：以为"学过"就该记住。

**实际规律**（第 8 天测验总结）：

| 内容 | 写过几遍 | 结果 |
|---|---|---|
| 服务端 | 2 遍 | ✅ 记得 |
| 状态机 | 3 遍 | ✅ 几乎全对 |

## 坑 45：launch 文件里写 `~`，路径不展开

**现象**：
```
Parameter file path is not a file: ~/ros2_ws/src/my_turtle/config/circle_params.yaml
```

**原因**：**`~` 只有 shell（bash）认识，会把它换成 `/home/pummy`。**
Python 字符串里的 `~` **就是个普通的字符**，launch 文件是 Python，所以它不会展开。

**解决**：写**真实绝对路径**：

```python
# ❌ 错
config_file = '~/ros2_ws/src/my_turtle/config/circle_params.yaml'

# ✅ 对（快速版，但把家目录写死了）
config_file = '/home/pummy/ros2_ws/src/my_turtle/config/circle_params.yaml'

# ✅ 最好（正规版，见坑 51）
import os
from ament_index_python.packages import get_package_share_directory
config_file = os.path.join(get_package_share_directory('my_turtle'), 'config', 'circle_params.yaml')
```

**教训**：**"shell 会做的事" ≠ "程序里也会做"。**
`~` 展开、`*` 通配、`$变量` —— 这些**都是 shell 的功能，不是文件系统的功能**。

## 坑 46：YAML 参数文件"静默失效"

**现象**：参数文件明明写了，程序也不报错，但**参数就是没生效**（用的还是代码默认值）。

**原因**：YAML 的**第 2 层固定要写 `ros__parameters:`（前后各两个下划线）**。
写成 `ros_parameters:` 或 `ros__parameter:` 都**不会报错**，只是读不到。

**正确的三层结构**：

```yaml
draw_circle:              # 第 1 层：节点名（必须和节点名一致）
  ros__parameters:        # 第 2 层：固定这么写，两个下划线！
    linear_speed: 6.0     # 第 3 层：参数名: 值
    angular_speed: 3.0
```

**三层各自的规则**：

| 层 | 写什么 | 写错的后果 |
|---|---|---|
| 1 | **节点名**（不带 `/`）| 对不上就整个读不到 |
| 2 | **`ros__parameters:`**（固定，两个下划线）| **不报错，但不生效** |
| 3 | `参数名: 值`（冒号后**必须有空格**）| YAML 语法错误 |

**教训**：**这是"静默失败"里最阴的一种 —— 没有报错，只是不干活。**
参数没生效时，**第一个要检查的就是 `ros__parameters:` 有没有写对**。

## 坑 47：接口包加 `--symlink-install` 会报错

**现象**：
```
existing path cannot be removed: Is a directory
```

**原因**：**接口包（`ament_cmake` + `rosidl`）与 `--symlink-install` 天生冲突。**

编译接口包时，工具链**自己会生成一个 Python 包目录**；
而 `--symlink-install` 想用软链接**覆盖那个目录** —— **软链接覆盖不了已经存在的目录**。

**规则**：

| 编什么包 | 加 `--symlink-install`？ |
|---|---|
| `my_turtle`（Python 包）| ✅ **要加** |
| `my_interfaces`（接口包）| ❌ **不加** |
| 全量 `colcon build` | **不加**（就三种，没有别的变体）|

> **用户的最终选择（第 11 天）**：**不建别名**，直接敲完整命令
> `colcon build --packages-select my_turtle --symlink-install`。
> 理由很正当：**命令显式、无隐藏配置、翻历史就能排查**。
> 别名只是"少打字"，代价是"多一份记忆 + 隐性行为" —— 包少的时候不值得。
>
> **另一条路**：工作空间根目录放 `colcon_defaults.yaml`，让 `colcon build` 自带默认参数。
> 但 `packages-skip` 设成默认后，想单独编 `my_interfaces` 时会和 `--packages-select` 打架，
> **所以不推荐。**

**教训**：**`--symlink-install` 不是万能的**，它和"编译时会自己生成文件的包"冲突。

## 坑 53：位置参数写成了 `=`（踩了两次）

**现象**：`SyntaxError`，或参数怎么都不生效。

```python
self.declare_parameter('side'=1.5)      # ❌
```

**原因**：**`=` 是"关键字参数"的写法；位置参数必须用逗号。**

```python

```

**什么时候能用 `=`**：只有明确写参数名时才行，比如
`declare_parameter(name='side', value=1.5)`。但**没必要**，按位置写最短。

**踩了几次**：第 10 天测验（`'turn_speed'=0.2`）、第 11 天测验（`'side'=1.5`）—— **两次**。

**教训**：**函数调用里的参数用逗号分隔**：`函数名(参数1, 参数2, 参数3)`。
`=` 只在"给某个具名参数赋值"时用。

## 坑 54：中文输入法打出了全角标点

**现象**：
```
SyntaxError: invalid character '（' (U+FF08)
```

**原因**：中文输入法下打出的是**全角**字符 —— `（ ）` `；` `：` `，` `“ ”`。
Python **只认半角** `( ) ; : , " "`。

**为什么难发现**：**全角和半角在你的编辑器里长得几乎一模一样**，圆括号有时完全看不出区别。

**怎么发现**：报错里会给出**字符的 Unicode 编码**：

| 编码 | 是什么 |
|---|---|
| `U+FF08` | 全角左括号 `（` |
| `U+0028` | 半角左括号 `(` |

**`FF` 开头的多半是全角字符。**

**解决**：写代码时**把输入法切到英文半角**。

**教训**：**报错里那个 `U+xxxx` 是线索，别跳过它。**

| ① | **`setup.py` 的 `entry_points` 没加那一行** | `grep 程序名 ~/ros2_ws/src/my_turtle/setup.py` |

1. 在 `my_turtle/my_turtle/` 里**建文件**

## 坑 56：类名 / 节点名 / 消息类型名 —— 三个"名字"混淆

**现象**（第 11 天用户的原话）：
> "想问节点名是对应着 Pose 库里的什么位置"

**原因**：以为"节点名"必须从某个消息类型里来。

**正确理解**：**这几个名字完全独立，互不相关。**

| 名字 | 写在哪 | 谁起、什么风格 |
|---|---|---|
| **类名** | `class Xxx(Node):` | **你**（驼峰：`StatusBridge`）|
| **节点名** | `super().__init__('xxx')` | **你**（小写下划线：`status_bridge`）|
| **消息类型名** | `create_publisher(Xxx, ...)` | 别人或你（驼峰：`TurtleStatus`）|
| **话题名** | `create_publisher(__, 'xxx', __)` | **你**（小写下划线，可带 `/`）|

**命名风格速查（混的根源就在这）**：

| 东西 | 风格 | 例子 |
|---|---|---|
| 文件名 | 全小写 + 下划线 | `status_bridge.py` |
| **类名** | **驼峰**（首字母大写）| `StatusBridge` |
| 节点名 / 话题名 | 全小写 + 下划线 | `status_bridge`、`/turtle_status` |
| **消息类型名** | **驼峰** | `TurtleStatus`、`Pose` |
| 变量 / 方法名 | 全小写 + 下划线 | `self.publisher_`、`operation` |

**教训**：**"驼峰的"和"小写加下划线的"是两拨东西** —— 记住这条就不会再混。

# 十三、自定义服务实战（第 12 天新增）

> 这一批坑来自"把 `draw_square` 升级成画**任意正多边形**"这个任务。
> 这是阶段三的收官任务。

## 坑 59：算"转了多少度"时，没处理 ±180° 的接缝

**现象**：画正多边形时，**某一个角的角度明显不对**（偏小）。五边形、三角形尤其明显。

**原因**：turtlesim 的 `msg.theta` **被限制在 -π ~ +π**，
跨过 180° 时会从 `+3.14` **跳到** `-3.14`（其实是同一个方向）。

```python
dtheta = abs(msg.theta - self.start_theta)      # ❌
```

**举例**（五边形，转弯角 = 360°/5 = **72°**）：`start_theta = 144°`，乌龟转到 `-179°`（等价于 181°）：

| | 值 |
|---|---|
| ❌ `abs(-179 - 144)` | **323°** → 以为转够了 → **提前停** |
| 实际只转了 | **37°** |

→ **那个角就只转了 37° 而不是 72°，形状歪掉。**

**解决**：把角度差**折回**到 (-180°, +180°]：

```python
dtheta = abs(math.atan2(math.sin(msg.theta - self.start_theta),
                        math.cos(msg.theta - self.start_theta)))      # ✅
```

**为什么这样对**：`sin` / `cos` 以 360° 为周期，
`sin(-323°)` 和 `sin(37°)` 完全相同；`atan2` 再从它们反解出落在 (-180°, 180°] 的角度。
**=-323° 被折回成 +37°。**

**为什么 `draw_square` 从来没暴露这个 bug**：
90° 的转弯正好**跨在接缝上** —— 它也在 180° 处提前停了，但**刚好停在正确位置**。
**歪打正着，问题被掩盖了。**

**教训**：
- **凡是"角度"参与运算，先问一句"它会不会跨过 ±180°"**
- 取最短角距离的万能写法：**`atan2(sin(Δ), cos(Δ))`**
- 正多边形边数 ≥ 3 → 转弯角 ≤ 120° < 180°，所以这个写法**永远正确**

## 坑 60：节点类名和 import 进来的服务类型**撞名**

**现象**：

```python
from my_interfaces.srv import DrawPolygon   # 此刻这个名字 = 服务类型

class DrawPolygon(Node):                    # ← 这行一执行，名字被【覆盖】成这个类！
```

**教训**：**import 进来的名字是整个文件共享的** ——
**给类起名前，先扫一眼自己 import 了什么。**

## 坑 61：以为服务回调可以"等任务做完" —— 会死锁

**现象（设计意图）**：想在服务回调里"等乌龟把多边形画完"，
好把真实结果填进 `response.corners_done`。

**为什么不行**：`rclpy.spin` 默认是**单线程**的 —— **一次只处理一个回调**。

```
① 服务回调开始执行，卡在里面"等画完"
② Pose 消息来了 → 但 spin 正忙着 → operation 回调【排不上队】
③ 乌龟不动 → 永远画不完 → 服务回调永远等下去
   = 死锁（整个节点冻住，连订阅回调都跑不了）
```

**解决**：服务回调**只下达任务、立刻返回**：

```python
response.success = True       # 含义是"【指令已受理】"，不是"画完了"
response.corners_done = 0     # 还没开始
return response
```

**真正的绘制**交给 `operation` 回调慢慢做。

**这里藏着"服务 vs 动作"的分水岭（重要）**：

| | 服务（Service）| 动作（Action）|
|---|---|---|
| 返回时机 | **立刻**返回 | 任务**做完**才返回结果 |
| 过程反馈 | ❌ 没有 | ✅ `goal_handle.publish_feedback()` |
| 取消 | ❌ | ✅ |
| 适合 | **快操作**（清屏、生成乌龟）| **长任务**（转 90°、画多边形）|

> **`RotateAbsolute` 为什么是动作而不是服务？**
> 因为"转 90°"**要花时间**，而且过程中想知道"还差多少"——**服务给不了这些。**
>
> **经验：长任务不要设计成服务。**

**教训（元层面）**：**服务的"一问一答"是瞬间的** ——
**别把"需要时间才能出结果"的任务塞进服务。**

## 坑 62：状态机没有"初始状态"，节点一启动就崩

**现象**：
```
AttributeError: 'PolygonDrawer' object has no attribute 'length_'
```
**而且是在服务还没被调用的时候就报了。**

**原因**：节点一启动，turtlesim 立刻开始发 Pose → 订阅回调立刻被调用 →
`if self.state == 'forward':` 成立 → 去读 `self.length_`，
但它是**服务回调里才赋值**的，此刻**属性还不存在**。

```
① 节点启动 → 建好订阅者
② turtlesim 每 0.016 秒发一次 Pose → 回调立刻执行
③ 进入 if self.state == 'forward' → 读 self.length_ → 不存在 → 崩
```

**解决**：给状态机一个**初始状态**：

```python
self.state = 'idle'      # 待机：什么都不做，只发零速度
```

服务回调接到任务后，才设成 `'forward'`。
（`'idle'` 会落到 `if/elif` 的 `else` 分支 → 发零速度 → 不会碰到那些还没赋值的属性。）

**教训**：
- **状态机的第一个状态必须是"待机"**
- **属性要在"可能被用到"之前就存在** —— 哪怕先给个 `0` 或 `None`

## 坑 63：服务能调很多次，但 `__init__` 只跑一次 —— 状态必须"每次"重置

**现象**：第一次调用服务正常画；**第二次调用，乌龟基本不动 / 乱动**。

**原因**：只在 `__init__` 里给了初始值，**没在服务回调里重置**。

> **`__init__` 只在【创建节点时】跑一次；而服务【可以被调用无数次】。**

```
画完第一个多边形之后的状态：
    state='done'   cnt=5   start_x=10.5   start_y=3.2

第二次调用服务（如果 srv 回调里不重置）：
    → handle_subs 看到 start_x 不是 None → 【不记录新起点】
    → dist 算的是"离【上一个多边形】起点的距离" → 一上来就超过边长
    → cnt 还是 5 → 立刻满足 cnt >= sides_ → state='done'
结果：乌龟基本不动
```

**解决**：**每次接到新订单，把状态退回初始值。**

```python
def reset_state(self):
    """把状态机退回初始状态（__init__ 和 服务回调 都调它）"""
    self.cnt = 0
    self.start_x = None
    self.start_y = None
    self.start_theta = None


def __init__(self):
    self.reset_state()
    self.state = 'idle'        # 开机：待机


def handle_srv(self, request, response):
    self.reset_state()         # ★ 每次新订单都退回初始状态
    self.state = 'forward'     # 接到订单：开工
```

**关键理解**：

> **`__init__` 管"开机时的初始状态"；
> 服务回调管"每次接到新订单时，把状态退回初始状态"。**
> **两者应该完全一致** —— 所以抽成一个 `reset_state()`，**只维护一份**。

**教训（DRY 原则：Don't Repeat Yourself）**：
> **同一份逻辑写在两个地方，早晚会不一致。**
> （项目里已经吃过这个亏：`00` 和 `04` 各维护一份目录树，结果数字对不上。）

## 坑 64：不知道该不该用"状态机"

**现象**：写节点时拿不准"这里要不要搞状态机"；
或者**明明需要却没搞**，导致每次回调都从零开始算。

**判据（一句话）**：

> **问自己：这次回调处理完之后，还有没有"下一次"需要用到这里的信息？**
>
> - **有** → 需要存进 `self.xxx` → 大概率就是状态机
> - **没有** → 不需要状态机

**对照表**：

| 节点形态 | 例子 | 要状态机吗 | 为什么 |
|---|---|---|---|
| 纯发布者 + 定时器 | `draw_circle` | ❌ | 每次干的事**完全一样** |
| 纯订阅者 | `read_pose` | ❌ | 每次干的事**完全一样** |
| **服务端（立即可答）** | `greeter` | ❌ | `request` 里啥都有，**一次算完就返回，没有"下一次"** |
| 发布 + 订阅（闭环）| `pubsub`、`draw_square` | ✅ | 要记住"**跑到哪一步了**" |
| **服务端 + 订阅者** | `turtle_control`、`draw_polygon` | ✅ **最典型** | 服务只"**点火**"，干活**分散在几十次回调**里 |
| 动作服务端 | `my_rotate_server` | ✅ 常见 | 长任务：发反馈、判断是否取消 |
| 定时器 + 分阶段任务 | （还没写过）| ✅ | "先走 2 秒 → 再转 1 秒 → 再走" |

**最典型的信号**：

> **一个回调负责"下命令"，另一个回调负责"干活"** ——
> 中间**必须有个东西记住"命令是什么、干到哪了"**，那就是状态机。

**反过来 —— 什么时候【不要】用**：

```python
# greeter 的服务回调：一次算完，根本不需要状态机
def handle_say_hello(self, request, response):
    response.success = True
    response.message = '你好！'
    return response
```

**过度设计的信号**：只有 2 个状态却搞出 5 个，还写了状态转移表。
→ **够用就行，别为了"像状态机"而状态机。**

**教训**：

> **状态机是"跨回调的记忆"，不是"每个节点都该有的东西"。**
> **没有"下一次"的地方，别硬造。**

# 十四、动作（Action）实战（第 13 天新增）

> 这一批坑来自"写第一个自定义动作服务端 `move_to_server`"这个任务。

## 坑 65：动作服务端要"边等边干" —— 单线程执行器会卡死

**现象**：`execute_callback` 里想读**订阅来的数据**（比如乌龟当前位置），
但那个值**永远是 `None` 或旧值**，任务卡住不动。

**原因**：`execute_callback` 是个**长时间运行的循环**，它一进去就**占住了执行器**：

```
execute_callback 开始执行 → 占住前台（rclpy.spin 默认单线程）
   ↓
它想读 self.latest_pose → 但订阅回调【排不上队】
   ↓
值永远是旧的（或 None）→ 乌龟不动 / 走错 → 任务卡死
```

**这是坑 61 的"动作版"**（那次是服务回调阻塞，这次是动作回调阻塞）。

**解决**：**请两个前台** —— 两处都要改，**缺一不可**：

```python
from rclpy.callback_groups import ReentrantCallbackGroup
from rclpy.executors import MultiThreadedExecutor

# ① 建一个"允许并发"的回调组，把订阅者和动作服务端都挂上去
self.cb_group = ReentrantCallbackGroup()
self.subscription = self.create_subscription(
    Pose, '/turtle1/pose', self.pose_callback, 10,
    callback_group=self.cb_group)
self._action_server = ActionServer(
    self, MoveTo, 'move_to', self.execute_callback,
    callback_group=self.cb_group)

# ② main() 里换成多线程执行器
executor = MultiThreadedExecutor()
executor.add_node(node)
executor.spin()
```

> **为什么两处都要改**：
> - **只加多线程执行器** → 回调都在默认的"互斥组"里，**还是排队**，没解决
> - **只加可重入组** → 执行器还是单线程，**只有一个前台**，也没解决

**代价**：两个线程可能**同时**碰同一份数据（`self.latest_pose`）。
本场景只读几个浮点数，风险低；但要意识到"并发安全"这个概念存在。

**教训**：
> **"会长时间运行的"回调** 和 **"要同时收数据"的需求**，天生冲突。
> 解法是 **多线程执行器 + 回调组**，**不是把循环写短**。

**来源**：
[Using Callback Groups（ROS 2 官方）](https://docs.ros.org/en/galactic/How-To-Guides/Using-callback-groups.html)、
[Deadlocks in rclpy（karelics）](https://karelics.fi/blog/2022/04/21/deadlocks-in-rclpy/)、
[rclpy issue #1598](https://github.com/ros2/rclpy/issues/1598)

## 坑 66：控制循环频率太低 —— 乌龟"一步跨过"目标

**现象**：让乌龟走到 (8, 8)，它**冲过去、来回抖**，永远停不下来。

**原因**：循环里写了 `time.sleep(0.5)` —— **每 0.5 秒才发一次速度指令**。

```
乌龟速度 1.5 米/秒 × 0.5 秒 = 一步走 0.75 米
容差只有 0.3 米
→ 一步就跨过目标，永远落不进容差里
```

**解决**：`time.sleep(0.5)` → **`time.sleep(0.05)`**（每秒 20 次）。

**教训（工程直觉，很重要）**：
> **控制频率必须比"任务变化的速度"快得多。**
> 发指令太稀疏 = **闭着眼睛大步走**。
>
> 这条以后做 Gazebo 仿真、调 Nav2 参数会**一直**遇到。

# 十五、换 API 时的习惯性错误（第 16 天）

## 坑 68：把"订阅者的四件套"套到"建服务"上

**现象**（第 16 天）：
```python
self.create_service(Trigger, 'say_hello', self.operation, 10)   # ❌ 多了个 10
```

**原因**：`create_xxx` 系列的**参数个数各不相同** —— 很容易"顺手多带一个"。

| 建什么 | 写法 | 参数个数 |
|---|---|---|
| `create_publisher` | `(类型, 话题, 队列)` | 3 |
| **`create_subscription`** | `(类型, 话题, 回调, **队列**)` | **4** |
| **`create_service`** | `(类型, 服务名, 回调)` | **3** |
| `create_client` | `(类型, 服务名)` | **2** |
| `create_timer` | `(间隔秒数, 回调)` | 2 |

**关键理解**：
> **"队列长度"只有【话题】才需要。**
> 因为话题是**持续广播的流**，订阅者跟不上时才要排队；
> **服务是"一问一答"，用完就丢，没有队列这个概念。**

**怎么自己查参数（万能办法）**：
```bash
python3 -c "import inspect, rclpy.node; print(inspect.signature(rclpy.node.Node.create_service))"
```

**教训 —— 这类错误的规律（重要）**：

> **刚写完 A，就把 A 的规则顺手带到 B 上。**
>
> | 坑 | 把谁的习惯带过来了 |
> |---|---|
> | **坑 53** | 写完 Python 字典 → 把 `=` 带到**位置参数**上 |
> | **坑 58** | 写完 Python 列表 → 把**逗号**带到 **CMake** 上 |
> | **坑 68** | 写完订阅者 → 把**队列长度**带到**服务**上 |
>
> **共同点：都是"上一个东西的习惯"。**
> **防法：换一个 API 时，先花 5 秒确认它的参数个数。**

# 十六、RViz 的显示问题（第 16 天）

## 坑 69：RViz 的 `RobotModel` —— `Status: Ok` 却什么都不显示

**现象**（第 16 天）：在 RViz 里加了 `RobotModel`，`Status` 显示 **`Ok`**，
但中间一片空白，**没有模型**。

**真正的原因**：**`Description Topic` 那一栏的【话题名是空的】。**

```
Description Topic: （空白）
```

→ RViz **建不出订阅** → **压根没去拿数据** → **但也不报错**
（"没在订阅"不算错误）。

**什么时候才暴露**：把那一块的 `durability` 改了一下之后，
RViz **才真的去尝试订阅** → 报出：

```
error subscribing: empty topic name
```

**解决**：在 `RobotModel` → `Description Topic` 里设置**两处**：

| 小栏 | 值 | 为什么 |
|---|---|---|
| **话题名** | **`/robot_description`** | ★ **必须填**（这就是真凶）|
| **`durability`** | **`transient_local`** | 见下 |

**为什么 `durability` 也必须改**：

`/robot_description` 是**锁存话题** —— 发布者**只在启动时发一次**。
按 ROS 2 官方文档的 QoS 兼容规则：

| 发布者 | 订阅者 | 能连上吗 | 结果 |
|---|---|---|---|
| Volatile | Volatile | ✅ | 只收"连上之后"的新消息 |
| Volatile | Transient local | ❌ **不能连** | |
| **Transient local** | **Volatile** | ✅ **能连** | 只收"连上之后"的新消息 —— **收不到那条锁存的历史消息** |
| Transient local | Transient local | ✅ | ✅ **收得到那条已经发过的** |

> **结论：发布者用 `transient_local` 时，订阅者【也】必须用 `transient_local`，
> 才收得到"启动时发过的那一条"。**

原理来源：[ROS 2 官方文档 · Quality of Service settings](https://docs.ros.org/en/humble/Concepts/Intermediate/About-Quality-of-Service-Settings.html)

**为什么这个坑特别难查（三条教训）**：

| # | 教训 |
|---|---|
| 1 | **`Status: Ok` ≠ 收到数据** —— RViz 的 Status 只表示"我没遇到错误"，**"还没收到数据"不算错误**。又一种"静默失败"（同坑 46、坑 48）|
| 2 | **`Subscription count: 0` 才是硬证据** —— 用 `ros2 topic info <话题> --verbose` 看：**订阅者数量为 0 = 根本没连上**（不是"连上但没数据"）|
| 3 | **出现了 `error` 就去读它的文字，不要靠猜** —— 见下 |

**同一个原因造成的第二个现象**：

```bash
ros2 topic echo /robot_description        # 什么都不打印
```

因为 `ros2 topic echo` 的默认 durability 是 **`volatile`** →
**连上了，但错过了那条锁存消息**。

**（给助手的教训 —— 这条很重要）**：

> 助手最初把原因猜成"**QoS 不兼容导致连接被拒**"—— **方向错了**。
> `TRANSIENT_LOCAL` 发布者 + `VOLATILE` 订阅者是**兼容**的，只是收不到历史消息。
> **真正的原因是"话题名空着"**，而这是靠那条 `error subscribing: empty topic name` 才定案的。
>
> **教训：在只有 `Status: Ok` 的阶段，任何"推测"都可能把排查带偏。**
> **"现象像" ≠ "已验证"。**

**给 RViz 的通用经验**：
> **RViz 里每个显示器（RobotModel / LaserScan / Image…）都有一栏"话题名"——
> 加完之后一定要确认它填上了。**
> **空白不会报错，只会安安静静地什么都不显示。**

# 十七、可动关节没有变换（第 17 天）

## 坑 70：可动关节"没有变换" —— `ros2 topic pub` 发的时间戳是 0

**现象**（第 17 天）：URDF 里加了一个 `continuous`（可动）关节，RViz 报

```
No transform from [wheel_left] to [base_link]
```

`ros2 topic hz /tf` 显示 **"topic [/tf] does not appear to be published yet"** ——
**`/tf` 存在，但一条数据都没有。**

而且 **`base_link` 自己也不是 TF 里的帧**（`tf2_echo` 报 `Invalid frame ID "base_link"`）。

**排查过程（值得学）**：把关节类型先改成 **`fixed`** 试一下：

```xml
<joint name="wheel_left_joint" type="fixed">
```

→ **轮子立刻出现了** ✅

**这一步把问题一刀切开**：
| | 结论 |
|---|---|
| `fixed` 能显示 | `robot_state_publisher` ✅、URDF ✅、RViz ✅ |
| `continuous` 不行 | **只有"可动关节"这条路不通** |

**真正的原因**：用 `ros2 topic pub` 手动发 `/joint_states` 时，
**消息的 `header.stamp` 是 `0`**（`ros2 topic pub` **不会自动填时间戳**）。

```
ros2 topic echo /joint_states --once
    header:
      stamp:
        sec: 0        ← ★ 就是这里
        nanosec: 0
```

**`robot_state_publisher` 不接受时间戳为 0 的关节状态 → 一条 `/tf` 都不发。**

**解决**：用一个**会填时间戳**的发布者发 `/joint_states`：

```bash
python3 -c "
import rclpy, time
from rclpy.node import Node
from sensor_msgs.msg import JointState
rclpy.init()
n = rclpy.create_node('fake_js')
p = n.create_publisher(JointState, '/joint_states', 10)
m = JointState()
m.name = ['wheel_left_joint']
m.position = [0.0]
while rclpy.ok():
    m.header.stamp = n.get_clock().now().to_msg()   # ★ 关键是这一行
    p.publish(m)
    time.sleep(0.05)
"
```

→ **轮子出现** ✅

**教训**：
> 1. **`ros2 topic pub` 不会自动填 `header.stamp`** —— 凡是**依赖时间戳**的节点
>    （TF、`robot_state_publisher`、`message_filters`、RViz…）都可能因此**静默不工作**。
>    **手动造数据时，记得填时间戳。**
> 2. **"先改成最简单的形式试一下"是个好排查手段** ——
>    把 `continuous` 换成 `fixed`，**一刀就把范围切成了两半**。
>    这比盯着 `/tf` 猜快得多。
>
> **正规做法**：用 **`joint_state_publisher`**（专门发 `/joint_states` 的标准工具，会填好时间戳）。
> **本机当时没装**（`ros2 pkg list | grep joint` 查不到），
> 要装的话：`sudo apt install ros-jazzy-joint-state-publisher ros-jazzy-joint-state-publisher-gui`。

# 十八、把模型塞进 Gazebo（第 19 天）

## 坑 71：`ros_gz_sim create` 报 "successful"，但 Gazebo 里没有模型

**现象**（第 19 天）：把 URDF 塞进 Gazebo 时

```
$ ros2 run ros_gz_sim create -topic /robot_description -name my_robot -z 0.5
[INFO] [ros_gz_sim]: Requesting list of world names.
[INFO] [ros_gz_sim]: Waiting messages on topic [/robot_description].
[INFO] [ros_gz_sim]: Entity creation successful.
```

**Gazebo 窗口里什么都没有**，而且：

```
$ gz model --list
Available models:
    - ground_plane          ← 没有 my_robot
```

**原因**：`-topic /robot_description` 要等的那个话题，**是 `robot_state_publisher` 发出来的**。

> **`robot_state_publisher` 没在跑（或后来被关掉了）→ `create` 永远等不到那个话题。**

**验证命令**：

```bash
ros2 node list        # 看 /robot_state_publisher 在不在
gz model --list       # 看世界里到底有什么模型
```

**解决**：**先起 `robot_state_publisher`，再起 `create`**。

```bash
# 终端 2（先起）
ros2 run robot_state_publisher robot_state_publisher --ros-args -p robot_description:="$(xacro <你的.xacro>)"

# 终端 3（后起）
ros2 run ros_gz_sim create -topic /robot_description -name my_robot -z 0.5
```

**另一个已验证可用的办法**：**用 `-file` 直接喂文件**（不依赖话题）

```bash
xacro <你的.xacro> > /tmp/r.urdf
ros2 run ros_gz_sim create -file /tmp/r.urdf -name my_robot -z 0.5
```

| | `-topic` | `-file` |
|---|---|---|
| 依赖 | **需要 `robot_state_publisher` 在跑** | **不依赖任何节点** |
| 好处 | URDF 改了**自动生效** | 需要每次重新 `xacro >` 一次 |

**教训**：
> 1. **`create` 报 `Entity creation successful` ≠ 模型真的出现在世界里** ——
>    那只说明"**服务调通了**"。**必须用 `gz model --list` 验证。**
> 2. **`-topic` 依赖另一个节点在跑** ——
>    **"话题必须有人发"**这条老规则的又一次现身（同坑 48、坑 69、坑 70）。
> 3. **`gz model --list` 是查"世界里到底有什么"的硬手段** ——
>    和 `ros2 node list` / `ros2 topic list` 是同一类"先看事实"的命令。

**（未确证的一条）**：最早那次失败（`create` 收到了消息、报了 success，但世界里仍没有模型），
**当时 `robot_state_publisher` 是在跑的** —— 所以原因**不是**上面这条。
**最可能是当时有两个 Gazebo 实例在同时跑**（一个在闪、一个后来启动的），
`create` 把模型发给了 GUI 没在看的那个服务端。**但这条没有验证过，只是推测。**
