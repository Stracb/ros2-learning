# 一、这套系统是怎么跑起来的

## 1.1 一共有几个程序在跑

以 `ros2 launch my_robot_description gazebo.launch.py` 为例：

```
ros2 launch ...
    │
    ├── gz sim                 ← 其实会 fork 出【两个】进程
    │     ├── 【server】          在背后算物理、算传感器（没有窗口）
    │     └── 【gui】             你看到的那个窗口（只是"显示屏"）
    │
    ├── robot_state_publisher   ← 一个 ROS 2 节点
    ├── ros_gz_sim create       ← 跑一下就退出的 ROS 2 节点
    └── ros_gz_bridge           ← 一个 ROS 2 节点

另外还有你自己另开的：rviz2
```

> ⚠️ **`gz sim` 不是 ROS 2 节点** —— 它说 gz-transport 的"语言"，**不在 `ros2 node list` 里**。

## 1.2 Gazebo 内部：**它自己也是一套"发布/订阅"** ⭐

**Gazebo 用自己的通信库（`gz-transport`），不是 ROS 2 的 DDS** —— **但架构几乎一模一样**：

| ROS 2 里 | Gazebo 里 | 说明 |
|---|---|---|
| 话题 | **话题** | 一样是"发布 / 订阅" |
| 服务 | **服务** | 一样是"一问一答" |
| 节点 | 没有对应概念 | Gazebo 里最接近的是"模型" |

> **对应的 gz 命令（看话题 / 看服务 / 看模型 / 看 URDF→SDF 转换结果）
> 统一在 `06-ROS2命令速查.md` §3.12「Gazebo / ros_gz 命令」—— 本文件不再列。**

**server 和 gui 之间就是靠这个通信的**：

```
【server】——持有"世界"：物理、模型、传感器
     │
     │  发布：世界状态、场景描述、传感器数据……
     ▼
【gui】——只是个客户端：订阅 server 的话题，画出来给你看
```

> ## **关键领悟**：
> ## **你在 Gazebo 窗口里看到的一切，都是 GUI【订阅 server 的话题】画出来的。**
> ## **GUI 本身不持有世界** —— **你看的其实是"server 的直播"。**
>
> **同理**：在 GUI 里拖动模型 → GUI **调 server 的服务** → server 改世界 → 再发布新状态 → GUI 更新 ✅

## 1.3 ROS 2 侧：谁在发、谁在收

| 话题 | 谁**发布** | 谁**订阅** |
|---|---|---|
| **`/cmd_vel`** | **你**（`ros2 topic pub`）| **bridge** |
| **`/scan`** | **bridge** | **RViz**（Add 了 LaserScan 之后）|
| **`/odom`** | **bridge** | （暂时没人）|
| **`/joint_states`** | **bridge** | **robot_state_publisher** |
| **`/robot_description`** | **robot_state_publisher**（latched）| **RViz 的 RobotModel** |
| **`/tf`** | **robot_state_publisher** | **RViz** |
| **`/tf_static`** | **robot_state_publisher** | **RViz** |

**Gazebo 侧（gz 话题）**：

| gz 话题 | 谁**发布** | 谁**订阅** |
|---|---|---|
| **`/cmd_vel`** | **bridge** | **server 里的差速驱动插件** |
| **`/scan`** | **server 里的 `gpu_lidar`** | **bridge**（+ gui，如果开了 `<visualize>`）|

**六个角色的身份总结**：

| 参与者 | 身份 |
|---|---|
| **server** | **既发又收**（产出传感器数据，也接收速度指令）|
| **gui** | **纯订阅者** |
| **bridge** | **每个话题上"一边收、一边发"** |
| **robot_state_publisher** | **既收又发**（收关节角度，发 TF 和 URDF）|
| **RViz** | **纯订阅者**（没有任何发布）|
| **你**（`ros2 topic pub`）| **纯发布者** |

## 1.4 `ros_gz_bridge` 的双重身份

**它不是"一根管子"，是"一个会说两种语言的节点"** ——
**每个话题上它都"一边收、一边发"**（收发方向见上一节 §1.3 的两张表）。

| 配置项 | bridge 内部做什么 |
|---|---|
| `direction: ROS_TO_GZ` | **在 ROS 侧订阅** + **在 gz 侧发布** |
| `direction: GZ_TO_ROS` | **在 gz 侧订阅** + **在 ROS 侧发布** |

> ## ⭐ **这解释了一个反复遇到的现象**：
> **`ros2 topic list` 里有 `/cmd_vel`，但一开始【没人在发】。**
> **它还"存在"，是因为 bridge 订阅了它** ——
> **ROS 2 的"话题图"由"谁发、谁收"共同组成，只要有订阅者，话题就出现。**

## 1.5 服务在哪儿：`ros_gz_sim create` 调的是服务

**Gazebo 也有服务**（`gz service -l` 可列）。

```
你: ros2 run ros_gz_sim create -file ... -x 3
        │
        └──► 调 Gazebo 的服务：/world/empty/create
                    │
                    └──► server 收到请求 → 把模型放进去 → 返回成功
```

**证据**（`gazebo.launch.py` 启动时会打印）：

```
[create-3] [INFO] [ros_gz_sim]: Requesting list of world names.
```

> **"话题 = 一直流" vs "服务 = 一问一答"** —— **`create` 问完就退出** ✅

## 1.6 为什么两边不能直连

| | ROS 2 | Gazebo |
|---|---|---|
| **通信库** | **DDS**（RTPS 协议）| **gz-transport** |
| **消息类型名** | `geometry_msgs/msg/Twist` | `gz.msgs.Twist` |
| **类型名的写法** | **用 `/` 分三段**（包/msg/类型）| **用 `.` 分两段**（gz.msgs.类型）|

> ## **同一件事（速度指令），两边的【名字】和【编码】都不一样。**
> ## **所以必须有 bridge 翻译** ✅

## 1.7 ⭐ 用【控制理论】再看一遍这套系统（第 28 天用户提问引出）

> **用户原话**："我基本懂了，按控制理论来说一遍流程可以吗"
>
> **这一节是给"学过自动控制"的人一张对照表** ——
> **它能把前面 1.1–1.6 的零散零件，装进一个熟悉的框架里。**

### 对照表

| 控制论概念 | 本系统 | 在哪一侧 |
|---|---|---|
| **参考值 `r(t)`** | **"往前走" / "到 (5,5)"** | 你的意图 |
| **控制器** | **你写的节点 / Nav2** | **ROS 2** |
| **控制量 `u(t)`** | **`/cmd_vel`（Twist）** | ROS 2 → gz |
| **前向通道** | **`bridge`（ROS_TO_GZ）** | bridge |
| **执行器** | **DiffDrive 插件 → 轮子** | gz |
| **被控对象（Plant）** | **车的动力学（DART 物理引擎）** | gz |
| **输出 `y(t)`** | **车的真实位姿** | gz 内部 |
| **传感器** | **`gpu_lidar` / 轮子编码器** | gz |
| **测量值** | **`/scan` `/odom` `/joint_states`** | gz → ROS 2 |
| **反馈通道** | **`bridge`（GZ_TO_ROS）** | bridge |
| **时间基准** | **`/clock`** | gz → ROS 2 |

> ## **⟹ bridge 在控制论上就是：【前向通道 + 反馈通道】。**

### 四个"用控制论才看得清"的点

**① 这是一个【闭环】系统**

```
读 /scan（反馈）→ 判断（控制律）→ 发 /cmd_vel（控制量）
```

**第 28 天写的那个"前方有东西就停"的节点，就是标准闭环控制器** ✅

**② ⭐ 坑 81 的本质是【反馈通道的信号质量】问题，不是控制器问题**

| 现象 | 控制论里的说法 |
|---|---|
| **一半采样全是 `inf`** | **50% 的测量无效** |
| **2 米以内固定测不到** | **测量在某个区间【完全失效】** |
| **控制器继续前进 → 撞墙** | **基于错误反馈做出的决策** |

> ## **⟹ 控制器参数调得再好，也救不了【反馈是假的】。**
> ## **所以：调控制器之前，先验证【反馈信号本身可不可信】。**

**第 28 天"记住上一次的有效值"那个补救，控制论上叫"用估计值补偿测量缺失"** ✅

**③ "停止发布 ≠ 停止运动" = 【零阶保持器】**

```
数字控制器输出离散序列 u[0], u[1], u[2] …
        ↓
被控对象需要连续信号
        ↓
中间必须有【保持器】
        ↓
★ DiffDrive 插件就是那个保持器：
   收到 u[k] 后一直用它，直到收到 u[k+1]
```

> ## **所以"不发新指令" ≠ "输出为 0" —— 要停车必须【显式发 0】。**
> ## **（这就是第 22 天那条"停止发布 ≠ 行为停止"的控制论解释。）**

**④ `/odom` 是【观测器输出】，不是真值**

| | 是什么 |
|---|---|
| **真值 `y(t)`** | **车的实际位姿**（藏在 Gazebo 内部）|
| **`/odom`** | **轮子积分得到的【状态估计】** |
| **它的毛病** | **打滑就错、误差会累积** —— **这是积分器的本性，不是 bug** |

**由此，`map` / `odom` 分层就是【两级观测器】**：

| | 怎么算 | 特性 | 控制论角色 |
|---|---|---|---|
| **`odom → base_link`** | **轮子积分** | **连续、会漂** | **高频平滑的局部估计** |
| **`map → odom`** | **激光比对地图** | **不漂、会跳** | **低频绝对的修正量** |

> ## **⟹ 这就是经典的【互补滤波】思想：
> ## 高频但漂移的估计 + 低频但绝对的修正。**

### 一句话总结

> ## **第 28 天那个"车不停"，不是控制器的错，
> ## 是【反馈信号来自一个不可靠的测量环节】。**
> ##
> ## **而"传感器是渲染出来的"这件事，本质上就是：
> ## 你的反馈信号来自一个【会有丢帧和盲区】的测量通道。**

## 1.8 SLAM 的核心概念（第 33 天讲透）

> **为什么放在这里**：SLAM 是一个**问题**，不是一个算法。
> 不把这六个概念理顺，看 `slam_toolbox` 那几十个参数就是天书。

### ① 鸡生蛋问题 —— SLAM 到底难在哪

| 你想做的事 | 前提 | 循环 |
|---|---|---|
| **建地图** | 得知道自己在哪 | ⬅ |
| **知道自己在哪** | 得有一张地图 | ⬅ |

**两个都需要，两个都缺。** 这就是 SLAM（Simultaneous Localization And Mapping）要解决的问题本身。

> 对比一下就更清楚：**导航（Nav2）是"地图已知，求路径"**；
> **SLAM 是"地图也没有，边摸边画"**。

### ② 扫描匹配 —— 怎么"同时"解开这个死结

**核心动作**：拿**当前这一帧点云的形状**，去和上一帧（或已有地图）比，
**试出一个"对齐得最好"的位姿** —— **一次同时算出平移和旋转**。

| 直觉上以为它做的事 | 它实际做的事 |
|---|---|
| 比较"正前方距离从 1.0 变成 0.8" | **把整帧点云拖来拖去，找出"和地图最吻合"的那个位置 + 朝向** |

**⟹ 这也是为什么"环境要有特征"**：如果四周看起来处处一样（比如两面平行的白墙之间的走廊），
**"对齐得最好"就有无穷多个答案** —— 这在学术上叫**退化（degeneracy）**。
**表现就是：地图沿那个方向漂、或者干脆叠出好几层墙。**

> ## **⚠️ 但是（第 36 天的教训）：看到"地图叠墙 / 墙距不对"，【先别怪退化】。**
> ## **本项目里那些症状的真因是【位姿方向反了】**（`08` 坑 95：URDF 轮子关节轴反 → 车实际后退、odom 报前进）。
> ## **排查顺序：① `gz model -p` 验 odom 方向 → ② 关掉匹配看是否仍错 → ③ 最后才怀疑环境退化。**

### ③ 漂移 —— 为什么"一帧一帧拼"注定不行

一帧对一帧地拼，**每一帧的小误差会累积**。走 10 米、转两圈之后，地图整体就歪了。

**这就是"航迹推算（dead reckoning）"的宿命** —— 和计步器在你家门口准、走到三条街外就不准，是同一件事。

### ④ 闭环检测 —— 怎么把累积的误差"拉回来"

**当机器人绕回一个来过的地方**，它有机会发现："这地方我见过！"
一旦确认，就能**把这圈的误差一次性摊掉**。

**两步走，各管一头**：

| 步骤 | 干什么 | 宁可 |
|---|---|---|
| **粗筛** | 用**低维描述子**快速挑出"可能来过"的候选 | **宁可多放进来**（漏了就没机会了）|
| **精验** | 对候选做**完整匹配**确认 | **宁可放过**（错了会把整张图拉歪）|

> ## **⟹ 假阳性（把没来过的地方认成来过）比漏检更糟** —— 漏检只是少修正一次，假阳性是**把地图整张搬走**。

**本项目的实测印证**：第 34 天里出现过一次 `map → odom` **突然跳到 −81°**、
地图上同一堵墙被画到好几个位置 —— **这正是"一次性大修正"的形状**，
和回环误判的表现一致（`slam_toolbox` 对应参数是 `do_loop_closing` / `loop_search_maximum_distance`）。

### ⑤ 图优化 —— 闭环之后地图为什么会"自己变直"

把所有关键帧当成**图的节点**、把帧间的相对位姿当成**边**，
闭环就是**加了一条"首尾相连"的边** —— 然后**整体求解一次**，让所有边尽量都满足。

| 你看到的 | 背后发生了什么 |
|---|---|
| 地图**突然整体变直**、位置跳一下 | **图优化跑了一遍**，把所有节点一起挪了 |

**⟹ 所以"地图突然跳"不一定是坏了** —— 可能正是它在修正。
**判断标准是：跳完之后【是不是更准了】**。

### ⑥ 和卡尔曼滤波的关系（最容易混的一个）

> ## **卡尔曼是【工具】，SLAM 是【问题】。**

| | 卡尔曼滤波（KF / EKF） | SLAM |
|---|---|---|
| 更新什么 | **只更新状态**（我在哪）| **状态 + 地图**一起更新 |
| 典型用途 | 传感器融合、姿态估计 | 建图 + 定位 |
| 谁在用 | `robot_localization`（EKF）| `slam_toolbox`（**用的是图优化，不是卡尔曼**）|

**一句话**：**能用卡尔曼的地方，是"地图已知或不需要地图"的地方**；
一旦地图也要一起估，就得上 SLAM 那套（图优化 / 粒子滤波）。

### ⑦ 落到本项目的四个环节

| 环节 | 谁负责 | 出了问题的典型现象 |
|---|---|---|
| **里程计**（`odom → base_link`）| `diff_drive_controller` | 车走直线、`odom` 却说拐弯 → 地图糊 |
| **扫描匹配 + 建图**（`/scan → /map`）| `slam_toolbox` | 墙叠成几层、出现幻影 |
| **闭环 / 图优化** | `slam_toolbox` | 地图**突然**跳一下、整体转向 |
| **重定位**（已知地图里定位）| AMCL（阶段九）| 定位跳变、粒子散开 |

> **⟹ 出问题时先分清落在哪一格** —— 四格的修法完全不同（`08` 坑 85–96 就是按这个顺序排的）。

# 二、"话题"这个模型的准确理解

## 2.1 话题 = 广播频道（**不是存储**）

> **发布者往里发，订阅者从里收。** ✅
>
> **但消息【发出去就没了】** —— **后来才订阅的人收不到之前的内容** ✅
> （除非 QoS 设成 `transient_local`，见 `06` §3.10）

**四个可以"空"的极端情况**（都踩过）：

| 情况 | 结果 |
|---|---|
| 有发布者、没订阅者 | 消息**白发了** |
| **有订阅者、没发布者** | **一直等，静默无反应** ← 坑 48 / 70 / 71 |
| 有发布、有订阅，但 **QoS 不兼容** | **还是收不到，也不报错** ← 坑 69 |
| 话题名 **空着** | **连订阅都没建** ← 坑 69 |

## 2.2 ⭐ 三层检查法（遇到"看不到 / 没数据"就按这个走）

| 层 | 问题 | 命令 |
|---|---|---|
| **①** | **这东西存在吗？** | `ros2 node list` / `gz model --list` / `ros2 topic list` |
| **②** | **有人在发吗？** | `ros2 topic hz <话题>` / `gz topic -l` |
| **③** | **我订阅上了吗？** | `ros2 topic info <话题> --verbose`（看 **Subscription count**）|

> ## **口诀**：**先看"东西在不在"，再看"在不在跑"，最后看"连没连上"。**
> ## **不要一上来就猜参数。**

**今天多学到的第四问**：

| **④** | **数据的【源头】对吗？** | 例：`ranges` 全是边界值 → 传感器底层没产出 |
|---|---|---|

## 2.3 QoS 的投递语义

# 三、TF 为什么要这么设计

## 3.1 URDF 是"静态结构"，`/joint_states` 是"动态角度"

| URDF 告诉我们的 | URDF **没**告诉我们的 |
|---|---|
| 轮子**装在**车体左边 0.2 米处 | 轮子**现在转到** 5 度了 |
| 激光雷达**在**车顶 0.12 米处 | —— |

**而 TF 要的是"此刻，A 相对 B 在哪、朝哪"** —— 所以需要**两部分拼起来** ✅

## 3.2 `robot_state_publisher` 的角色：**加工者**

```
【输入】
  · /robot_description   ← URDF（启动时读一次）：车的结构
  · /joint_states        ← 关节当前角度（持续订阅）
        ↓ 换算
【输出】
  · /tf_static           ← 固定关节的变换（只发一次）
  · /tf                  ← 可动关节的变换（持续发）
```

| 关节类型 | 需要 `/joint_states` 吗 | 走哪个话题 |
|---|---|---|
| **`fixed`** | ❌ **不需要**（位置永远不变）| **`/tf_static`** |
| **`continuous` / `revolute` / `prismatic`** | ✅ **需要** | **`/tf`** |

> **所以"轮子没有 TF"的根因永远是【没人发 `/joint_states`】** ✅ —— 见坑 70。
>
> ⚠️ **`robot_state_publisher` 只在启动时读一次 URDF** ——
> **改了 URDF 必须重启它** ✅

## 3.3 ⭐ 为什么 `/tf` 和 `/tf_static` 要分开

**根本原因：两种数据的【投递语义】不同，而 QoS 只能按话题设。**

| 话题 | 装什么 | 频率 | QoS | 为什么 |
|---|---|---|---|---|
| **`/tf`** | 可动关节 | **几十 Hz** | **`volatile` + 队列短** | 高频，**要新的，不要旧的** |
| **`/tf_static`** | 固定关节 | **只发一次** | **`transient_local`** | 一次性，**但"谁来了都给"** |

**合并会怎样**：

```
合并成一个话题 /tf
    静态变换需要 transient_local（后订阅的也要拿到）
    动态变换需要 volatile（高频，绝不能缓存）
              ↓
    只能选一个 ❌
      选 transient_local → 高频数据疯狂堆积 → 内存爆
      选 volatile        → 后启动的 RViz 拿不到静态变换 → 机器人画不出来
```

> **历史补充**：**ROS 1 早期就是只有一个 `/tf`**，
> **后来（Indigo 前后）才拆出 `/tf_static`** —— **不是没人想过，是做过了发现该拆** ✅

## 3.4 `tf2_buffer`：**底层分开、上层统一**

```
【传输层】—— 分开的两个话题
    /tf           （高频、volatile）
    /tf_static    （一次性、transient_local）
          │  两者都被喂进
          ▼
【存储层】—— tf2_buffer（每个进程里各有一份，把两条流合成一棵带时间戳的树）
          │
          ▼
【使用层】—— lookupTransform("base_link", "laser_link")
    你查的时候【根本不用管】它来自哪个话题 ✅
```

> ## **"分不分"是【传输层】的问题；"用起来是不是一体"是【库层】的问题。**
> ## **两个问题被解耦了** ✅
>
> **推广**：**底层分开传、上层合并用** —— 传输的复杂度和使用的简单性分别优化。
> 同类例子：`/tf` + `/tf_static` → `tf2_buffer`；msg/srv/action 三种接口 → `import` 一下就用。

## 3.5 为什么"两边各算一遍"

```
Gazebo 的 server
    · 它算物理 → 它【自己知道】每个零件在哪
    · 但它说 gz-transport 的"语言"，ROS 2 侧听不见

ROS 2 侧
    · 想要 TF → 只能【自己再算一遍】
    · 用什么算？URDF（结构）+ /joint_states（角度）
    · 谁来算？robot_state_publisher
```

> **两边能对齐，靠的就是 Gazebo 把【真实的关节角度】通过 `/joint_states` 送过来** ✅
> （这就是"关节状态插件"存在的意义）

## 3.6 三种"视角"：`base_link` / `odom` / `map`

> **每个坐标系 = 一个"站在哪里看世界"的立场**（第 29 天用户用"视角"这个词，很准）

| 坐标系 | **站在哪看** | **原点是什么** | **谁定的** | **性质** |
|---|---|---|---|---|
| **`base_link`** | **车里** | **车的某个参考点** | **你（URDF）** | **逻辑原点** |
| **`odom`** | **出发的地方** | **车启动那一刻的位置** | **DiffDrive 插件（轮子积分）** | **连续、会漂** |
| **`map`** | **地图上** | **地图的固定点（SLAM 定的）** | **SLAM / 定位节点** | **不漂、会跳** |

**用一句话把三种视角串起来**：

```
在 base_link 里：  "障碍物在我【左前方 0.3 米】"
        ↓ 加上"车相对起点走了多远"（odom → base_link）
在 odom 里：       "障碍物在【起点前方 5.3 米】"
        ↓ 加上"起点在地图的哪儿"（map → odom）
在 map 里：        "障碍物在【房间东南角】"
```

> ## **⟹ 同一样东西，换一个坐标系，就换一种说法。TF 就是这些说法的翻译字典。**

**类比**：

| 坐标系 | 像什么 | 回答的问题 |
|---|---|---|
| **`base_link`** | **你的身体** | "东西在我身上的哪个方位" |
| **`odom`** | **计步器** | "我离出发点走了多远" |
| **`map`** | **GPS** | "我在城市的哪个位置" |

**两个器官都有，但你不会用计步器去找自己的手** ✅ —— 所以"手离我多远"用 `base_link`、"我在房间哪"用 `map` ✅

### ⚠️ "最初的原点"有两层答案，别混

| 说法 | 答案 | 为什么 |
|---|---|---|
| **"逻辑上最先定义的坐标系"** | **`base_link`** | **URDF 里就有，所有零件相对它定位** |
| **"树上的根 / 绝对零点"** | **`odom`（现在）→ `map`（以后 SLAM）** | **根没有父亲，它的原点就是这套系统的绝对参照** |

## 3.7 怎么看 `view_frames` 的"一大坨"输出

**格式是"每个坐标系一段"**：

```
wheel_left:                        ← 子坐标系的名字
  parent: 'base_link'              ← ★ 只看这行：父亲是谁
  broadcaster: 'default_authority' ← 没用（看不出来是谁发的）
  rate: 20.408                     ← ★ 每秒发几次
  most_recent_transform: 454.022   ← 最新一条的时间戳
  oldest_transform: 451.572
  buffer_length: 2.450
```

### ⭐ 只看两行：`parent` 和 `rate`

| 字段 | 用来看什么 |
|---|---|
| **`parent`** | **树的结构**：谁挂在谁下面 |
| **`rate`** | **静态还是动态**：**`rate: 10000` + `most_recent_transform: 0` = 静态**；真实频率（20.4 / 50.2）= 动态 |

### 找"根"的方法

> **根 = 那个【只当父亲、从来没当过孩子】的坐标系。**

**操作**：把所有 `parent:` 后面的名字收集起来 → 再把所有"冒号前的名字"（子）收集起来 → **在前者里、不在后者里的，就是根**。

**例**：

```
孩子：wheel_left, wheel_right, laser_link, caster_*, camera_link
父亲：base_link（全部）
⟹ base_link 出现在"父亲"里、不在"孩子"里 → 根是 base_link

★ 但正确应该是 odom → 说明 odom → base_link 那条边没了
```

**⟹ 所以"根不是 `odom`" 是【TF 树断了】最快的一个信号** ✅

## 3.8 "绝对坐标"在哪：树根 vs Gazebo 的世界原点

**TF 里【每条边都是相对位姿】** ✅ —— 没有任何一条边说"我在世界的绝对位置" ✅

**但树有一个根，根没有父亲** ✅ —— **根的原点就是这套系统的"绝对零点"** ✅

### ⚠️ Gazebo 有它自己的"世界原点"，但它【不在 TF 里】

| "世界原点" | 谁定的 | 在 TF 树里吗 |
|---|---|---|
| **Gazebo 世界的 `(0,0,0)`** | **仿真器** | ❌ **不在** |
| **`map` 的原点** | **SLAM** | ✅ **在**（树根）|
| **`odom` 的原点** | **车启动那一刻** | ✅ **在**（现在的树根）|

**为什么 Gazebo 的世界原点不在 TF 里**：

- **TF 是 ROS 2 的概念** ✅ —— 它只知道 ROS 2 的坐标系
- **Gazebo 的世界是仿真器内部的概念** ✅ —— 它不向 TF 报"我也有个原点"
- **所以"车在 `(5,0)`"和"`odom → base_link` 是 `(5,0)`"这两件事【碰巧一致】，但没有机制保证**

> ## **⟹ TF 里【没有"世界"这个坐标系】。**
> ## **最上游的是 `map` 或 `odom`，它们的原点就是这个系统的绝对零点。**

### 所以"绝对"是相对的

```
你的 odom 原点 = 车启动的位置
    ↓ 换个地方启动，odom 原点就换了
    ↓ 那"绝对坐标 (5,0)"说的是什么？
    ↓
★ 它说的是"相对你自己的起点 5 米"
```

**这和经纬度不同** —— 经纬度有物理意义（地球）；`odom` / `map` 的原点是**约定的** ✅

### 真要跟"世界"对齐怎么办

**加一条 `world → map` 的静态变换**：

```bash
ros2 run tf2_ros static_transform_publisher 0 0 0 0 0 0 world map
```

**这样就人为地把 `map` 原点钉在"世界原点"上** ✅

| 场景 | 需要吗 |
|---|---|
| 只是自己跑仿真 | ❌ 不需要 |
| 多机器人协同（要知道彼此相对位置）| ✅ 需要 |
| 和真实地图 / 卫星坐标对齐 | ✅ 需要 |
| Nav2 某些配置 | 有时会要求有个 `map` |

## 4.3 ⚠️ "改了但没生效"（★ 最容易被反复踩的一族）

|---|---|---|

> ### ⭐ `ament_cmake` 包里，**哪些改了要重编**（第 30 天助手答错过一次，用户纠正）
>
> | 改了什么 | 要重编吗 |
> |---|---|
> | **`.py` 节点源码**（`ament_python` 包）| ❌ **不用**（软链）|
> | **`launch/` 里的 launch 文件** | ✅ **要** |
> | **`config/` 里的 yaml** | ✅ **要** |
> | **`urdf/` 里的模型** | ✅ **要** |
> | **`worlds/` 里的世界文件** | ✅ **要** |
> | **`rviz/` 里的配置** | ✅ **要** |
> | **`CMakeLists.txt` / `package.xml`** | ✅ **要** |
>
> > ## **一句话：`ament_cmake` 包里，【除了 Python 源码，什么都要重编】。**
> > ## **因为它所有东西都是【拷贝】进 `install/` 的。**
>
> **⚠️ 最坑的一点**：**改了 launch 文件【不报错、也不生效】** ——
> **因为 launch 用的是 `install/` 里那份旧拷贝，而你改的是 `src/` 里那份** ✅
> **（"定义了但没启动"和"改了源文件没重编"，是两种不同的静默失败。）**
| **重编了还是没变** | **没 `source`** | 坑 28 |
| **改了 URDF，Gazebo 里没变** | **世界里的那台模型是旧的** —— 要重新 `create`（或重启）| 坑 71 |
| **改了 URDF，RViz 里没变** | **`robot_state_publisher` 只在启动时读一次** —— 要重启它 | 本文件 3.2 |
| **改了 SDF 里的 `<pose>`，位置不变** | **`ros_gz_sim create` 的 `-x -y -z` 会【覆盖】SDF 里的 pose** | 坑 75 |
| **改了传感器参数，`ranges` 一点不变** | **底层根本没产出**（不是参数问题）—— 见 4.1 里"边界值"那两行 | 坑 72 |
| **新装的包 `ros2 launch` 找不到** | **没重编 / 那个终端没 source** | 坑 28 |

> ## **通用习惯**：
> ## **"改了没效果"的第一反应，不是继续调参数，
> ## 而是【确认改动真的到了"运行的那一份"里】。**
>
> **手段**：`gz sdf -p` 看转换产物、`grep` install 副本、`ros2 topic echo` 看实际值。

**三步确认法**（"改了没生效"逐层剥下来）：

| # | 确认什么 | 手段 |
|---|---|---|
| **①** | **源文件真的改了吗** | `grep` 源文件 |
| **②** | **改动真的编译 / 安装过去了吗** | `grep` install 副本、`gz sdf -p` 看转换产物 |
| **③** | **运行的那个进程重新加载了吗** | 重启节点 / 重启 Gazebo |

## 4.4 坐标系 / TF 不对

# 五、通用排查方法

## 5.1 三层检查法

> **完整那张表（含第四问"源头对吗"）在本文 §2.2** ——
> **一句话版：① 存在吗 → ② 在发吗 → ③ 我订阅上了吗 → ④ 源头对吗。**

## 5.2 反向实验

**做法**：**把某个参数改到【极端】，看现象有没有响应。**

| 例子（第 23 天实际用的）| 结论 |
|---|---|
| 把 `range_min` 从 `0.1` 改成 `1.0` → **RViz 里的圈跟着变大** | ✅ **确认"数值恒等于 `range_min`"** → 不是"被挡住"，是"底层没产出" |

> ## **用途**：**判断"某条数据链路活没活"。**
> **有响应 = 链路是活的（问题在别处）；没响应 = 链路在这之前就断了。**

## 5.3 二分法

**做法**：**把可疑的东西一个个拿掉，看现象是否改变。**

| 例子 | 结论 |
|---|---|
| 去掉 `laser_link` 的 visual / collision → 现象没变 | ❌ **不是"被几何体挡住"** —— 排除一个方向 |

> ## **用途**：**"说不清哪里出问题"时最可靠的手段** —— 比继续调数值靠谱得多。

### ⚠️ 但二分法有一个**前提**：**一次只改一个变量**

> **第 31 天（`ros2_control` 那次）换来的教训：**
> **我们做了十几个"排除实验"，但每次都在同时改【两个以上的东西】**
> （URDF + yaml + launch 一起动），**所以每次排掉的结论都不可信**，
> **最后 2 小时过去，仍然不知道根因。**

**正确做法**：

```
① 先有一个【确定能跑】的基线
② 只改【一个】变量
③ 验证
④ 通过 → 保留这个改动（它成了新基线）
   不通过 → 撤销这一改，换下一个变量
```

> ## **⟹ "一次一个变量"不是教科书上的讲究，是【不是这样就没法定位】。**

**反例（第 31 天真实发生的）**：

| 实验 | 同时变了什么 | 结果 | 能得出什么结论 |
|---|---|---|---|
| A | 换 URDF **+** 换 yaml | 成功 | ❓ 不知道是哪个起作用 |
| B | 换 URDF **+** 用自己的 yaml | 失败 | ❓ 不知道是哪个的问题 |
| C | 极简 URDF **+** 官方 yaml | 失败 | ❓ 同上 |

**⟹ 三个实验做完，一个可信结论都没有。**

## 5.4 ⭐ "改了但没生效"清单

> **完整表格 + 三步确认法都在本文 §4.3** —— **这里不再抄第二份**，只留指路。
>
> **一句话：** **"改了没效果"的第一反应，不是继续调参数，
> 而是【确认改动真的到了"运行的那一份"里】。**

## 5.5 先看事实，再猜原因

> ## **这是从坑 48 / 69 / 70 / 71 / 72 里总结出来的同一句话。**
>
> **"看不到 / 没数据"时，第一件事永远是跑查看类命令：**
> `ros2 node list` / `ros2 topic list` / `ros2 topic info --verbose` /
> `gz model --list` / `gz topic -l`

**为什么**：**"静默不工作"是这个系统里最常见的失败模式** ——
**它不报错，只"没反应"**，所以**只能靠"看事实"来定位**。

## 5.6 报错信息怎么用

| 步 | 做什么 |
|---|---|
| **1** | **读报错里的【答案部分】** —— 很多报错第一句就说了原因（如 `because existing path cannot be removed`）|
| **2** | **搜关键字** —— 去 `08` 的「按报错原文查」 |
| **3** | **报错没线索时，转去"看事实"**（5.5）|

## 5.7 ⭐ 给命令时守三条规矩（第 24 天用四个多小时换来的）

**背景**：第 24 天排查雷达时，助手给的命令**错了三次**，每次都让人以为"系统坏了"：

| # | 命令 | 错在哪 | 造成的误判 |
|---|---|---|---|
| **1** | `gz topic -e ... \| sort -n \| head` | **`gz topic -e` 永不结束，而 `sort` 必须等 EOF** → 永远不输出 | "四面墙也看不到" |
| **2** | `... \| grep -E "^ +[0-9]"` | **`--field ranges` 的实际格式不是"空格 + 数字"** | "ROS 2 侧全是 inf" |
| **3** | 改成正则 `"^- [0-9]"` | **`--field` 的输出格式又和"完整消息"不一样** | 又数出 0 |

**可靠的命令**（已验证）：

| 场景 | 用什么 |
|---|---|
| **看数据到底有没有** | **`ros2 topic echo /scan --once`** ← **不加 `--field`、不加 `grep`** |
| **数雷达有多少个有效值** | **`ros2 topic echo /scan --once \| grep -c "^- [0-9]"`** |
| **看 Gazebo 侧原始数据** | `gz topic -e -t <话题>` **+ `grep` / `head` 收尾**（命令族见 `06` §3.12；**看完 `Ctrl+C`**）|

**三条规矩**（**可执行**，不是空话）：

| # | 规矩 | 为什么 |
|---|---|---|
| **①** | **先给"看原始输出"的命令** —— 如 `ros2 topic echo /scan --once`，**不加 `--field`、不加 `grep`** | 先确认**现象真的存在**，再谈过滤和统计 |
| **②** | **命令要"会自己结束"** —— 用 `--once` / `timeout` / `head`；**别在"永不结束的流"后面接 `sort` / `wc`** | `gz topic -e` 永不结束 → `sort` 永远等不到 EOF → 没输出 |
| **③** | **不确定输出格式时，先 `\| head -c 300` 看一眼**，再写过滤命令 | 加不加 `--field`，`ros2 topic echo` 的输出格式**不一样** |

> ## **结论**：**"命令没输出" ≠ "现象不存在"。**
> ## **但在动手改系统之前，先把"看原始输出"这一步做掉。**

## 5.8 ⭐ 完整案例：「地图全错」的七层排除（第 33–36 天）

> **症状**：`slam_toolbox` 能跑、`/map` 有数据，但**墙的间距不对**、**同一堵墙出现两三条**、**RViz 里激光红点"跟着车走"**、`map→odom` 会跳。
>
> **这张表就是"下次遇到同类问题该按什么顺序查"的答案。** 每一层都先给出**一条能证伪的命令**，再往下走。

| 层 | 怀疑的东西 | 一条命令 / 一个做法 | 结论 | 结果 |
|---|---|---|---|---|
| **1** | **显示（RViz）** | **存一张 `.pgm`**（纯数据，不经 RViz），或 `map_saver_cli` | PGM 也一样歪 | ❌ 显示无罪 |
| **2** | **传感器数据** | 写**扫描探针**：读固定方位的距离，和几何真值比 | 正前 3.766（真值 3.75）、正后 3.749、左右 inf、**柱子回波落在 (1.01,0.70)，与盒子角一致** | ❌ 扫描无罪 |
| **3** | **时间** | 自写**延迟探针**（`use_sim_time:=true`，算 `now − stamp`）| **12 毫秒** | ❌ 时间无罪 |
| **4** | **坐标系** | `tf2_echo base_link laser_link` + `ros2 topic hz /tf` + `ros2 param get ... update_rate` + `gz topic -e -t /world/default/stats` | 旋转是单位矩阵、TF 100/50 Hz、**RTF = 1.0** | ❌ TF 与仿真都无罪 |
| **5** | **实时链路** | **录 `ros2 bag` → 关掉 Gazebo → 离线回放** | **离线也照样歪** | ❌ 实时性无罪（且造出了实验台）|
| **6** | **算法（扫描匹配 / 回环）** | 参数文件里 `use_scan_matching: false` + `do_loop_closing: false`，**`param get` 确认** | **位姿 = 纯 odom，地图仍然歪** | ❌ 匹配器无罪 |
| **7** | **位姿本身** | **`gz model -m my_robot -p`（物理真值）** 对比 `odom` | 真值 **−1.7305** vs odom **+1.7305**：**方向相反、大小一致** | ✅ **根因**（`08` 坑 95）|

### 两个转折点（记住这两个，比记住命令有用）

| 转折 | 为什么关键 |
|---|---|
| **第 1 层：用"纯数据"反驳"显示"** | 不做这一步，后面可能一直在分析**一个显示 bug**（用户当时就怀疑 RViz）|
| **第 6 层：关掉算法，仍然错** | **"关掉某功能也照样错" = 错在更底层。** 这一刀把范围从"算法"砍到"位姿"，直接指向根因 |

### 走错的五个岔路（全部记下来，因为它们看起来都很合理）

| 岔路 | 为什么合理 | 怎么排掉的 |
|---|---|---|
| `frame_id` 是怪名字 | 日志里真有一句 `Registering sensor: [Custom Described Lidar]` | 探针读到 `frame_id: laser_link` |

> ## **"输入 → 过程 → 环境"，一层一层往下砍；每一层都用一条【能证伪】的命令，而不是一句推理。**

### 5.8.1 ⭐ 补一维：**"现在干净" ≠ "当时干净"**（第 39 天的教训）

> **七层阶梯是按"模块"排的，但还有一种错是按【时间窗】藏的。**

**第 39 天的实例**：`/scan` **现在**的最小距离是 1.235 m（干净极了），
但**建图那 1–2 秒**里（车正从 0.3 米高处落下），雷达扫到了自己的车顶边缘 ——
那 12 个点被写进地图，**还把画布撑大了 3 倍**。

**⟹ 所以七层之外，再问一句：**

> ## **"这份数据是在【什么时候】采的？那段时间系统处于什么状态？"** ✅
> ## **典型的高危时间窗**：刚启动（节点还没就绪）、刚 spawn（模型在掉落/弹跳）、
> ## 刚切换控制器、刚恢复出厂设置、刚插拔传感器。

**它为什么骗人**：**你复现的时候，瞬态已经过去了** —— 你怎么测都正常，于是把"传感器"排除掉，
转而怀疑算法。**这正是它藏得深的原因。**
